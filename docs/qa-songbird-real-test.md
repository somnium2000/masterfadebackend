Este PR conecta el puente existente al SDK 2.5.8 real para lookup/continue. No se han ejecutado operaciones de proveedor. La prueba siguiente requiere autorización separada de publicación, migración local a QA, configuración y operación Sandbox; este documento no las ejecuta.

1. Operador: tras esa autorización, verificar ambos HEAD desplegados y aplicar únicamente `20261116003000_pixelpay_songbird_operational_context.sql` sobre la migración de handoff #128 ya existente. Su ausencia bloquea START antes de enviar la Sale. El PR no aplica migraciones remotas.
2. Mantener los controles existentes de una cuenta interna activa/autenticada y cliente verificado, rol, sesión y CSRF; Sandbox SDK, endpoint/app URL `https://pixelpay.dev`, sesión QA con caducidad. Mantener apagados piloto legado, Sale general, VIP y simuladores. Con autorización operativa, activar los ajustes existentes `QA_PIXELPAY_SONGBIRD_BRIDGE_ENABLED` y su clave AES de 32 bytes en el backend. Nunca entregar esa clave ni credenciales PixelPay a React. La elegibilidad debe confirmar booking, diagnóstico Sandbox y puente; VIP/Sale general continúan apagados.
3. Desde la cuenta QA, crear una reserva **nueva** de L 1.00 HNL y un intent nuevo. Usar exclusivamente los datos oficiales del caso 2.9 y el vencimiento del ejemplo SDK vigente; no copiar datos a logs. Los holds QA mantienen sus 30 minutos. La lease 3DS vence al menor plazo entre intent/holds, diez minutos y `exp` del JWT si existe; la sesión QA no extiende esos plazos.
4. Enviar una sola Sale inicial por el checkout. Al recibir 202/songbird, el backend correlaciona el contexto con la orden/monto/moneda y claim de esa Sale, conserva JWT/contexto cifrados y expone únicamente el handoff de consumo único. Pulsar una vez **Iniciar autenticación 3DS**. React carga Songbird Sandbox, el SDK genera los datos EMV y el backend ejecuta `CardinalAuthentication.authenticationLookup(new LookupTransaction())`; solo una respuesta válida con acción `continue` y ACS Sandbox acreditado abre el desafío.
5. Completar el desafío si aparece. Solo el evento `SUCCESS` con JWT puede solicitar `CardinalAuthentication.authenticationContinue(new LookupContinueTransaction())`, utilizando el identifier guardado del lookup. ERROR/FAILURE/NOACTION/CANCEL/TIMEOUT cierran localmente la autenticación sin llamar a continue ni Sale. Cada fase reclama su estado durable antes de IO. Recarga, timeout, duplicados, caducidad y pérdida de respuesta no reemiten la llamada ni reentregan el JWT. Consultar únicamente estado local.
6. Registrar solo HTTP, etapa, código y resultado sanitizados. El resultado más avanzado habilitado es la respuesta real de continue, seguida de `PIXELPAY_SONGBIRD_AUTH_RESULT_UNACCREDITED` cuando es HTTP 200/success. **No se envía un segundo POST Sale y no se confirma la cita por autenticación.** Ante rechazo o incertidumbre, detener la prueba de ese intent. La conciliación v2 con evidencia financiera auténtica y callbacks existentes se conserva.

## Límite exacto restante

`CardinalAuthentication.authenticationContinue()` retorna un `Response` genérico, no una entidad que acredite aprobación 3DS. `CardinalManager` llama a `retryTransaction()` incluso si continue devuelve `success=false`; por eso no se utiliza ese camino financiero. Para habilitarlo faltan el campo/contrato positivo autenticado de continue y la semántica de identidad/no duplicación de `authentication_identifier` en el segundo POST Sale. No existe una variable de este PR que convierta HTTP 200, el evento del navegador o la autenticación en pago.

La variante `202/songbird` con `collection_url` queda detenida con `PIXELPAY_SONGBIRD_DIRECT_API_UNSUPPORTED`: el SDK usa otra entrada (`CardinalManager.init(jwt, collection_url)`), que el puente actual no acredita. Un ACS ajeno a los dos orígenes staging cerrados se detiene con `PIXELPAY_SONGBIRD_CHALLENGE_UNACCREDITED`; no se amplían dominios por entrada del navegador.

## Retirada

Apagar el puente/sesión cierra nuevas operaciones; claims e identificación durable QA permanecen. Las leases vencen y no se recuperan operaciones inciertas. Revertir ambos PR restaura el puente cerrado; la columna privada nueva puede permanecer sin eliminar datos. No hay rollback de pagos ni cambios del contrato financiero v2.
